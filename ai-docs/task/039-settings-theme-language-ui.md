## 目标与背景

Rust 已有 Settings、Theme、Language 服务，QML 有设置窗口和语言页，但主题选择和界面语言切换尚未形成完整、可发现的 Settings 流程。当前 Rust 支持目录仅列出 `en`、`zh-CN`，与实际构建出的翻译资源必须保持一致。用户需要在 Settings 中切换界面主题和语言，并让语言目录成为单一、可校验的数据源。

## 范围与非目标

- 在 Settings UI 提供主题与应用界面语言选择；主题和语言继续由 Rust Settings/Theme/Language 服务持有并持久化，QML 不维护第二份已提交状态。
- 补齐并校验应用界面语言目录：每个可选 locale 均有可加载的翻译资源和明确的显示名称，构建资源、Rust 支持目录与 UI 选项一致。
- 语言切换先验证资源可加载，再提交 Rust 设置；失败时保留旧语言与界面，错误可见。
- 主题仅选择仓库当前支持的主题；外部用户主题编辑、导入/导出及文档排版主题不属于本任务。
- 不扩大文档正文的 BCP 47 语言能力；界面语言与文档排版语言继续分离。

## 前置条件与待决策

- 核实现有 ThemeService 是否已支持主题候选验证、提交和持久化；缺少的能力沿 Settings 服务补齐，不在 ViewModel 或 QML 另建状态机权威。
- 盘点仓库实际翻译目录后再确定可选 locale；没有完整翻译资源的语言不能只因系统 locale 可解析就出现在可选列表。
- 明确语言切换即时生效还是重启生效，并在实施前结合 Qt Translator 生命周期写入界面架构。

## 实施步骤

1. 盘点 Settings 对话框、Rust 服务、ViewModel、翻译文件与 CMake/qrc 注册，列出缺失语言和主题链路。
2. 设计 Rust 提供的 locale 元数据（规范 locale、显示名称、资源状态），使选择器不靠 QML 临时推导支持范围。
3. 接通主题与语言草稿、校验、提交、持久化、即时投影及失败恢复。
4. 增加服务、跨层和 Qt 测试，检查切换失败、重复选择、重启恢复和翻译资源缺失。
5. 更新运行时、QML 与 task-index 文档，执行独立 final review。

## 验收标准

- [ ] Settings 中可访问主题与界面语言选择，当前值与 Rust 持久化快照一致。
- [ ] 提交后界面主题/翻译按约定生效；重启后恢复所选值。
- [ ] 选择失败不改变当前设置或已显示的主题/语言，并呈现可理解的错误。
- [ ] locale 目录与实际构建翻译资源一致，无重复 locale、缺失资源或不可达选项。
- [ ] 应用界面语言与 `.cdoc` 的正文语言分离，Rust 是持久化状态的唯一权威来源。
- [ ] Rust、Qt/QML 测试、格式和 lint 通过；独立评审无未解决问题。

## 风险与回退

Qt 翻译器切换若在 Rust 提交后失败，会造成设置与界面不一致。应先在临时候选中加载资源，成功后再提交并替换当前翻译；任何失败都保留上一个可用快照。
