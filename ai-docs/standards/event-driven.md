# 事件驱动与调度

更新日期：2026-10-26。

## 原则

- 默认订阅真实状态变化，并在收到事件后更新派生状态；不通过周期检查猜测状态是否变化。
- 多个同步失效通知可合并到当前事件循环尾部。Qt/QML 中优先用 `Qt.callLater` 加一个 pending 标志合并同一轮的布局、缩放、滚动和主题事件；回调入口先清除标志，再处理最新状态，确保处理期间到达的新事件可以再次调度。
- 依赖绘制节奏的工作应接入对应的帧/场景图生命周期，不使用任意固定间隔模拟帧率。不得在场景图渲染线程调用 Rust Session、ViewModel 或 GUI 对象。
- 无事件源时才考虑轮询；必须说明为什么无法订阅、轮询间隔、资源成本、退出条件和失败/重试策略。固定频率健康检查或低频对账应有明确产品需求。

## 定时器适用条件

定时器本身不是轮询。只在功能具有明确时间语义时使用，例如光标闪烁、动画、用户可感知的 debounce、超时截止和带退避的重试。每个定时器需明确：

1. 它表达的时间语义和可接受延迟；
2. 谁拥有它，何时启动、停止、取消或重置；
3. 触发时已有新状态时如何丢弃旧工作，重复触发是否幂等；
4. 窗口隐藏、Session 替换和对象销毁后的行为；
5. 验证如何控制时间或观测触发顺序，避免靠长 `sleep` 的脆弱测试。

不要用 debounce 推迟文本、光标或选区的可见更新。若需要限制高频输入造成的重复计算，使用有界节流或事件循环合并，并在新内容到来时保证渲染追上最新 generation；刷新机制不得让持续输入一直重置截止时间。

## 评审检查

- 事件源是否覆盖所有相关变更？是否会漏失事件或在对象销毁后回调？
- 工作能否在同一事件循环或同一显示帧中合并？空闲时是否完全停止？
- 定时器是在表达真正的时间要求，还是仅为等待“也许发生了变化”？
- 定时器和异步回调是否校验 Session/document generation，避免过期结果覆盖新状态？
- UI 线程是否同步执行了可能阻塞输入或绘制的长任务？调度改进是否掩盖了根本耗时？
